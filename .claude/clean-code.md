# Clean Code — стандарт кода проекта

Весь код пишется по философии Роберта Мартина («Чистый код»).
Каждая строка — это письмо будущему читателю.

---

## 1. Именование

- Имена раскрывают намерение: `daysSinceCreation`, не `d`
- Избегай дезинформации: не называй список `accountList`, если это не `List`
- Используй произносимые имена: `generationTimestamp`, не `genymdhms`
- Одно слово на концепцию: не мешай `fetch`, `retrieve`, `get` для одного и того же
- Имена классов — существительные (`Customer`, `Parser`). Имена методов — глаголы (`save`, `delete`, `render`)

## 2. Функции

- **Маленькие** — функция помещается на экран (до ~20 строк)
- **Один уровень абстракции** — не смешивай высокоуровневую логику с деталями реализации
- **Делают одно дело** — если можешь описать функцию через «и», разбей её
- **Нет побочных эффектов** — функция делает то, что написано в её имени, и ничего скрытого
- **Разделяй команды и запросы** — функция либо *делает* что-то, либо *возвращает* что-то, но не оба действия
- **Минимум аргументов** — идеально 0–2. Три — уже подозрительно. Больше — почти всегда признак проблемы

## 3. Комментарии

- **Хороший код не требует комментариев** — если нужен комментарий, сначала попробуй переименовать или разбить функцию
- Допустимые комментарии: юридические заголовки, пояснение намерения (когда иначе нельзя), предупреждения о последствиях, `TODO`-пометки
- Недопустимые комментарии: перефразирование кода, закомментированный старый код, журналы изменений в коде

## 4. Форматирование

- **Вертикальная плотность** — связанные строки рядом, несвязанные разделены пустыми строками
- **Сверху вниз** — высокоуровневые функции вверху файла, детали ниже
- **Горизонтальная читаемость** — строки до ~120 символов
- Придерживайся принятых в проекте соглашений форматирования

## 5. Обработка ошибок

- **Исключения, не коды ошибок** — возвращаемые коды ошибок засоряют вызывающий код
- **Не возвращай `null`** — лучше пустой объект, `Optional`, или исключение
- **Не передавай `null`** в функции — это источник `NullPointerException`
- Пиши тесты, которые проверяют граничные случаи обработки ошибок

## 6. Тесты (F.I.R.S.T.)

| Буква | Принцип | Описание |
|-------|---------|----------|
| F | Fast | Тесты запускаются быстро |
| I | Independent | Тесты не зависят друг от друга |
| R | Repeatable | Работают в любой среде |
| S | Self-Validating | Результат — только «прошёл» или «упал» |
| T | Timely | Пишутся до или вместе с продуктовым кодом |

- Одна концепция на тест
- Тест — это живая документация: показывает, как код должен использоваться

## 7. Классы

- **Маленькие** — не по количеству строк, а по количеству **ответственностей**
- **SRP** — у класса одна причина для изменения
- **Высокая связность** — методы класса используют большинство его полей
- Если класс описывается через «и» — скорее всего, его нужно разбить

## 8. Архитектура

- **Разделяй инициализацию и использование** — логика запуска отдельна от бизнес-логики
- **Четыре правила простой архитектуры (Кент Бек):**
  1. Выполняет все тесты
  2. Не содержит дублирования (DRY)
  3. Отражает намерения автора
  4. Минимум классов и методов
- **Правило зависимостей** — зависимости указывают только внутрь (к бизнес-правилам), никогда наружу (к фреймворкам, БД, UI)

## 9. Запахи кода — признаки, требующие рефакторинга

- Длинный метод / большой класс
- Длинный список параметров
- Дублирование кода
- Комментарии вместо говорящего кода
- Мёртвый код (закомментированный или недостижимый)
- Цепочки вызовов (`a.b().c().d()`)
- Завистливые функции (метод больше использует данные другого класса, чем своего)

---

## Процесс написания кода

1. **Сначала заставь работать** — напиши «грязный» рабочий вариант
2. **Потом сделай чистым** — рефактори небольшими шагами, не меняя поведение
3. **Покрой тестами** — тесты дают уверенность при рефакторинге
4. **Правило бойскаута** — если трогаешь код, оставь его лучше, чем нашёл
